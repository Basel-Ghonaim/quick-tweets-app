# ADR 0007: Pre-auth Ingest — the Upload-Grant Authorization Model

> **Status:** Proposed
> **Date:** 2026-07-17
> **Deciders:** Basel Ghonaim

## Context

[ADR 0005](0005-media-file-upload-architecture.md) Decision 5 settled the write boundary: ingest runs under an **identified principal** — an authenticated user, or *a principal being created (as in register-with-avatar)* — **never anonymously**; every `MediaObject` records its **uploader**; Media authorizes an attach against that owner; and a feature's write endpoints accept **only media references, never file bytes or multipart**. It deliberately left open *how* an ingest binds to a principal that does not yet exist.

The first consumer forces the question. [#256](https://github.com/Basel-Ghonaim/quick-tweets-app/issues/256) (register-with-avatar) uses the **upload-then-submit-reference** client pattern: the avatar uploads *before* the register request completes, so at ingest time there is **no user row and no session**. The [Media execution plan](../../plans/media-implementation.md) names this decision a likely sub-ADR, gated before M6; it is settled **ahead of that gate, before M4**, because the ingest boundary's *authorization contract* (who may call it) and the registry's *uploader-provenance modeling* (deliberately deferred out of M2) both depend on it — deciding now means M4 is built once against the final model.

The threat this ADR bounds: an unauthenticated write path combined with the public `GET /media/:token` read is, unbounded, **an anonymous file host** — storage, bandwidth, and illegal-content hosting served from the application's domain.

This is a security-boundary authorization decision spanning Media, the auth feature, and the client pattern, and it sets a pattern intended to outlive its first consumer — [ADR 0002](0002-refined-adr-threshold.md) criterion 2, the same shape as its parent ADR 0005. It records boundaries, ownership, and invariants; mechanisms and values are deferred to the implementation Work Items.

## Decision

1. **The upload grant — a bearer capability, not a session.** Pre-auth ingest is authorized by a short-lived, server-minted **upload grant**: a capability that authorizes exactly one narrow action class — *ingest up to a bounded number of objects while the grant lives, and adopt what it ingested* — and nothing else. It is deliberately **not** a session or provisional account: it carries no subject identity, accumulates no state, authenticates no person, and is **spent** at adoption — spending ends the grant for every purpose (no further ingest, no further adoption). It satisfies Decision 5's "identified principal, never anonymous" as **identity-as-accountability** — it identifies the *upload episode* for provenance and abuse-bounding, not the person. Media owns minting, honoring, and expiring grants; the capability is feature-agnostic.

2. **Bounded at mint, bearer at presentation.** Possession of the grant authorizes ingest; the security boundary is not *who holds it* but the **multiplicative bounds around it**: rate-limited minting — keyed by a dimension the client cannot forge (the keying and any aggregate cap are implementation choices; a client-forgeable key is inadmissible) — a time-to-live, and a per-grant object count, composed with the settled size limit and content-authoritative validation (ADR 0005 Decision 7). The *existence* of these bounds is architectural; their **values are implementation choices** in the Work Items. Binding a grant to device, browser, or network context is **not** part of the security boundary — the threat is abuse-of-write, not account takeover, and a stolen grant's blast radius is a handful of small, validated images, or the one-shot adoption of them — though recording the minting origin as *forensic provenance* is an admissible implementation choice.

3. **Provenance: a grant-ingested object records the grant as its uploader.** Decision 5's "every `MediaObject` records its uploader" holds uniformly: for pre-auth ingest, the recorded uploader is the **grant identity** until adoption binds a real owner. Ingest is therefore never anonymous even before the principal exists.

4. **Adoption is attach with grant evidence — one mechanism, two evidence types.** The general rule remains Decision 5's: *Media authorizes an attach against the object's recorded uploader.* This ADR fixes the two admissible forms of authorization evidence: **an authenticated principal matching the recorded uploader**, or **presentation of the grant that ingested the object**. Register completion presents the reference *and* its grant after the user row exists; the attach then binds final ownership to the new user. Consequences of this shape:
   - **Media owns the operation** (it is the only writer of registry state); **the feature owns the trigger** — auth calls Media's published interface at the moment registration completes. The dependency direction of ADR 0005 Decision 2 is unchanged; adoption is one call across it, not a shared workflow.
   - Adoption is a **narrow, one-time provenance write on a ready object** — an explicit, bounded exception alongside the status transition (`ready` → `deleted`). It does **not** erode immutable-once-ready: the object's bytes, verified type, and storage key never change.
   - A leaked reference token alone is **not adoptable**: adoption re-requires the grant.

5. **No new lifecycle state — the grant TTL is the opportunity window.** An unadopted object remains an ordinary `ready` object; nothing in its persisted state changes when its grant ends. ADR 0005 Decision 8's invariant — *an object is never reclaimed before it has had the opportunity to be referenced* — receives its first concrete instantiation: **while the grant lives, adoption may still come, and reclamation must not touch the object; once the grant is no longer live — expired, or spent by an adoption that did not include the object — no adoption path remains** (grants do not renew), and the object is definitively abandoned. "Abandoned" is a **classification reclamation computes** from Media's own state (unadopted ∧ grant no longer live) — never a persisted status. Until reclamation exists (M11), abandoned objects remain ordinary, publicly servable `ready` objects — the mint bounds limit their *accumulation rate*, not their existence — an interval accepted as the cost of the plan's sequencing.

6. **No special read semantics.** Grant-ingested objects are **ordinary objects**. ADR 0005 owns the read-semantics rules (not servable until ready; permanent failure once deleted); the read boundary (the plan's M5) ships an *interim* public posture behind a documented resolution-time access seam — a posture owned by the deferred media access-posture decision; this ADR **deliberately does not exercise that seam** — servability is not conditioned on adoption or attachment. Doing so would entangle read semantics with coordination state and narrow a settled contract from the wrong owner. The abuse vector is bounded entirely on the **write side** (Decision 2 above) and by **lifecycle** (Decision 5 above).

7. **A reusable pattern, a single consumer.** *Pre-auth ingest* — mint a bounded grant → ingest under grant provenance → adopt when the principal materializes → expire unadopted — is a **general pattern** for any flow whose bytes precede their owning principal (registration now; e.g. invite-acceptance or onboarding flows later). Registration is its first consumer; **no generalization machinery** (grant-type registries, multi-flow configuration) is built until a second consumer exists — the same stance the storage-adapter port takes toward its second backend.

Narrowly for M6: adoption **constitutes the reference-begins signal on the register path**. The general reference-coordination contract (how any feature signals a reference begins and ends) remains a separate deferred decision, due before M9 and M11 — it is **not** decided here.

## Alternatives considered

- **Multipart on the register request** (create the user, then ingest the bytes it carried). Rejected: register is a feature write endpoint, and ADR 0005 Decision 5 is settled verbatim — feature endpoints *"accept only media references, never file bytes or multipart."* Special-casing register reopens a boundary this ADR has no authority over.
- **A provisional principal / registration session** (a first-class pre-auth identity that uploads and is later converted). Rejected: an identity container invites accretion — state, TTL extensions, attributes — growing a shadow auth system beside the real one. A single-purpose capability is the smallest thing that satisfies "identified, never anonymous."
- **Register first, upload after, under a real session** (no pre-auth surface at all). The strongest rival, and rejected **on product grounds, honestly recorded**: the register form ships an avatar input today (#256's context), ADR 0005 anticipated the being-created-principal flow by name, and the plan's M6 describes it. Beyond plan-consistency: it yields **partial-success account states** (register succeeds, then validation rejects the avatar — an account the user didn't submit, a softer rerun of #256) — a class the chosen design *narrows* (validation moves pre-submit) rather than eliminates (an adoption failing at the grant's edge, after the user row exists, is handled by the M6 Work Item) — and it forfeits **pre-submit validation feedback**, while the upload-then-submit pattern must exist *anyway* for the second consumer (tweet-compose attaches media before the tweet exists). Absent that product shape, this alternative would be the natural design — the pre-auth surface exists because the product requires it, and the grant is the smallest architecture that serves it.
- **Context-bound grants** (device/browser/network binding as the security boundary). Rejected as boundary: near-zero theft value against real false-positive cost on the most friction-sensitive flow. Forensic provenance recording remains admissible implementation.
- **Attachment-conditioned servability** (an object serves only once referenced). Rejected: it entangles read semantics with coordination state, and it would exercise the read boundary's access seam — which is owned by the deferred media access-posture decision, not by this ADR.

## Consequences

- **M4** builds the single ingest boundary against this model from the start: one route, **two authorization evidence types** (authenticated principal | upload grant), with the Media-owned, feature-agnostic mint capability beside it.
- **Uploader-provenance modeling** is deferred to M4's Issue — how the registry represents grant-then-user provenance (e.g. a nullable user reference completed by the one-time adoption write, or a distinct provenance field) — bounded by: the registry is the single owner of the record, a `MediaObject` remains unaware of its *referrers* (ADR 0005 Decision 9 — the uploader is provenance, not a referrer), and the adoption write of this ADR — plus two obligations: attach authorization always targets *current ownership* (after adoption, the user — never the retained grant provenance), and the abandonment classification (Decision 5 above) must remain computable from Media's own state (a stateless grant representation must still leave the grant's liveness derivable at ingest).
- **Grant representation** (stateless signed token vs persisted record), TTL / object-count / mint-rate values, and the mint route's shape are implementation choices in the Work Items; the API contract is updated when the routes are implemented (co-versioning).
- **The M6 client pattern** is fixed in shape: obtain a grant → upload (validated pre-submit) → submit the reference with the grant on register. The second consumer reuses the same pattern minus the grant (its evidence is the authenticated principal).
- **Reclamation (M11)** computes abandonment for grant-ingested objects from non-adoption plus the grant no longer being live (expired or spent), from Media's own state — consistent with Decision 8's conservative invariants; no new registry status is introduced by this ADR.
- This ADR is **immutable once accepted**; its status moves from `Proposed` to `Accepted` on merge. A future change to this model — including any additional evidence type beyond the two fixed here — is a new, superseding ADR.
